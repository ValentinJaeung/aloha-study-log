### 알게 된 것 3가지

1. **여기서 말하는 "epoch"은 데이터 전체를 한 번 훑는 단위가 아님.**
   `utils.py`의 `EpisodicDataset.__len__`이 에피소드 개수(50)를 반환하고,
   `__getitem__`이 에피소드당 **랜덤 타임스텝 1개만** 뽑음
   → 1 epoch = 45 샘플 ≈ 6 배치. 2000 epoch가 40분이면 끝나는 이유가 이것.
   저자가 "loss가 평평해진 뒤에도 더 학습하면 성공률이 계속 오른다"고 한 것도
   같은 맥락으로 보임 → **성공률이 낮으면 epoch를 늘리는 게 비용 부담이 거의 없음**
   (5000 epoch ≈ 100분).
2. **체크포인트는 100 epoch마다 저장** (`imitate_episodes.py:380`, `if epoch % 100 == 0`).
   개당 336 MB × 21개 + `policy_best` / `policy_last` ≈ **약 7 GB**.
3. **ResNet18 pretrained 가중치(44.7 MB)를 최초 1회 다운로드**함
   (`~/.cache/torch/hub/checkpoints/`). 이제 캐시되어 본 학습에선 이 단계 없음.

## 결과 / 관찰

### 1. WSL viewer 오류 — `OpenGL.error.Error: Attempt to retrieve context when no valid context`

WSLg는 `WAYLAND_DISPLAY`를 설정해둔다. PyOpenGL이 이 변수를 보고 백엔드를 **EGL**로 추측하는데
(`OpenGL/platform/__init__.py:36`), 정작 GLFW는 **X11/GLX** 컨텍스트를 만든다.
서로 어긋나서 `eglGetCurrentContext()`가 `None`을 반환 → 위 오류.

`~/.bashrc`에 3줄 추가로 해결:

```bash
export MUJOCO_GL=glfw
export PYOPENGL_PLATFORM=glx
export GALLIUM_DRIVER=d3d12
```

### 2. 렌더링이 CPU로 돌고 있었음 (llvmpipe)

GPU/CUDA는 정상인데(RTX 2080 Ti, `torch.cuda.is_available() = True`) **OpenGL만** 소프트웨어
래스터라이저를 쓰고 있었다. WSLg용 하드웨어 드라이버 `d3d12_dri.so`는 설치되어 있는데 자동 선택이 안 됨.

| 백엔드 | RENDERER | MuJoCo 오프스크린 렌더링 (480x640) |
|--------|----------|------------------------------------|
| 기본 | llvmpipe (LLVM 20.1.2) | 33.3 fps |
| `GALLIUM_DRIVER=d3d12` | D3D12 (NVIDIA GeForce RTX 2080 Ti) | **156.7 fps** |

약 **4.7배** 차이. 데이터 수집/평가 렌더링 시간이 그만큼 줄어든다.
`MESA_LOADER_DRIVER_OVERRIDE=d3d12`는 효과 없고 `GALLIUM_DRIVER=d3d12`만 동작함.

### 3. 자잘한 것들

- `record_sim_episodes.py`의 인자는 `--onscreen`이 아니라 **`--onscreen_render`**
- `visualize_episodes.py --episode_idx`에는 파일명이 아니라 **숫자만** 넣는다 (`episode_{idx}.hdf5`로 조립됨)
- 데이터는 `act/dataset/`이 아니라 `~/aloha_project/aloha_data/sim_transfer_cube_scripted/`에 있음.
  `act/`에서 실행하면 `--dataset_dir ../aloha_data/...`
- 레포에 **mp4를 재생하는 코드는 없다.** `act-plus-plus/replay_episodes.py`는 이름과 달리
  저장된 action을 시뮬에서 다시 실행해 *새* mp4를 만드는 스크립트다.
  → 재생용으로 `act/play_video.py`를 따로 만들어 둠 (`q`로 종료)

# 2026-09-18 (개념) — 시뮬 데모는 누가 만들고, 정책은 뭘 배우는가

**목표**: "teleoperation도 아닌데 시뮬 안에서 팔이 어떻게 움직이지? 코드가 움직인 거면
학습에 의미가 있나?"라는 의문을 코드로 확인

## 한 일

- `ee_sim_env.py` / `sim_env.py` / `scripted_policy.py` / `record_sim_episodes.py`를 읽고
  데모 생성 경로를 끝까지 추적
- MJCF(`assets/*.xml`)에서 mocap body와 weld 구속을 확인
- 스크립트가 쓰는 정보와 정책이 받는 정보를 비교
- 정리 결과를 [docs/01-act-sim.md](../docs/01-act-sim.md) "⭐ 개념 정리" 섹션에 기록

## 결과 / 관찰

### 1. 시뮬의 "사람 손" = MuJoCo mocap body

`assets/bimanual_viperx_ee_transfer_cube.xml:6-7`에 mocap body가 로봇 손목에 **weld(용접)**
구속으로 붙어 있고, `ee_sim_env.py:58-74`가 매 스텝 이 mocap을 목표 pose로 옮긴다.
mocap은 물리를 무시하고 순간이동하는 "유령 손잡이"라서, 이걸 끌면 weld를 만족시키려고
**물리 솔버가 알아서 관절을 푼다.**

→ **IK를 푸는 코드가 레포에 없다.** 실기에서 사람이 leader 팔을 손으로 끄는 것과 같은 구조.

그 손잡이를 끄는 건 `scripted_policy.py:88-98`의 waypoint 테이블(시간축 키프레임 몇 개)이고,
`interpolate()`가 사이를 선형보간한다.

### 2. 데이터 수집이 2단계인 이유 (제일 헷갈렸던 부분)

`record_sim_episodes.py`는 에피소드 하나당 시뮬을 **두 번** 돌린다.

1. `ee_sim_env` + scripted policy 실행 → 나온 **관절 궤적 `qpos`만 뽑아둠** (`:74-82`)
2. `sim_env`에서 그 관절 궤적을 **action으로 재생**하며 이미지/qpos 기록 (`:96-110`)

실기에서 저장되는 건 EE pose가 아니라 **leader 팔의 관절각(= follower 목표 관절각)**이기
때문. 1단계의 EE 제어는 데모를 *만드는 수단*일 뿐이고, 최종 데이터 포맷은 실기와 1:1로 같아야 한다.
2단계에서 `BOX_POSE[0] = subtask_info`로 같은 물체 배치를 강제하는 것도 이 때문.

→ hdf5에는 **EE pose도 물체 좌표도 안 들어간다.** 이미지 / qpos / qvel / action 뿐.

### 3. ⭐ 핵심: 스크립트와 정책이 보는 정보가 다르다

| | 스크립트 (데모 생성) | ACT 정책 (학습 대상) |
|---|---|---|
| 큐브 위치 | `env_state`에서 **정답 좌표를 그대로 읽음** (`scripted_policy.py:73-74`) | ❌ 못 봄 (`policy.py:19`에서 `env_state = None`) |
| 입력 | 특권 정보 | 카메라 이미지 + 현재 관절각 |

게다가 큐브 위치는 에피소드마다 랜덤이다
(`ee_sim_env.py:162` → `utils.py:133` `sample_box_pose()`, `x∈[0,0.2] y∈[0.4,0.6]`).

→ 이 학습은 "코드가 시킨 대로 따라하기"가 아니라
**정답을 아는 스크립트 → 카메라만 보는 신경망으로의 증류(distillation)** 다.
정책은 ① 픽셀에서 물체 위치 추정 ② visuomotor 매핑 ③ action chunking(100스텝 통째 예측)을
새로 배운다. 스크립트에는 이 중 아무것도 없다. **그래서 학습에 의미가 있다.**

### 4. 그리고 ACT는 강화학습이 아니다

`policy.py`의 loss는 `L1(정답 action, 예측) + kl_weight × KL`이 전부. **보상 항이 없다.**
시뮬의 `reward`는 데모 성공 판정과 eval 성공률 측정에만 쓰인다.
→ 데모를 사람이 만들든 코드가 만들든 **학습 구조는 완전히 동일**하고, 바뀌는 건 데이터의 질뿐.

### 5. scripted 데이터의 한계

- `record_sim_episodes.py:31`에 **`inject_noise = False`가 하드코딩**되어 있음.
  `scripted_policy.py`에는 `±0.01` 노이즈 주입 코드가 있는데 안 쓰이고 있다.
- 따라서 큐브 좌표가 같으면 궤적이 항상 똑같다 → **멀티모달리티가 0**.
- ACT의 CVAE(style variable `z`, KL 항)는 원래 사람 데모의 멀티모달리티를 다루려고 있는 건데,
  scripted 데이터에서는 그 효용이 거의 드러나지 않는다.

## 결과 ⭐ 기대치(≈90%) 달성

| | temporal_agg 끔 | temporal_agg 켬 |
|---|---|---|
| **Success rate** | **0.94** (47/50) | **0.98** (49/50) |
| Average return | 592.66 | **669.04** |
| 소요 시간 | 9분 32초 (572초) | 15분 19초 (919초) |
| 영상 | `rollouts_no_agg/` | `rollouts_temporal_agg/` |

**temporal ensembling이 +4%p, average return은 +13%.** 대신 시간은 1.6배.

### 보상 단계별 분포 — 실패가 어디서 나는지

`sim_transfer_cube`의 최대 보상은 4이고 단계마다 1씩 오른다.

| 도달 보상 | 의미 | agg 끔 | agg 켬 |
|---|---|---|---|
| ≥ 1 | 오른팔이 큐브에 접촉 | 48/50 (96%) | **50/50 (100%)** |
| ≥ 2 | 큐브를 집어 듦 | 48/50 (96%) | 49/50 (98%) |
| ≥ 3 | 왼팔로 전달 시도 | 47/50 (94%) | 49/50 (98%) |
| ≥ 4 | **전달 성공(= 성공 판정)** | 47/50 (94%) | 49/50 (98%) |

- **실패는 거의 전부 파지(grasp) 단계에 몰려 있다.** 집기만 하면 전달은 사실상 따라온다
  (agg 끔: 48 → 47, agg 켬: 49 → 49).
- temporal_agg가 개선한 지점도 정확히 거기다. 접촉 실패 2건이 0건이 됐다.
  매 스텝 여러 chunk의 예측을 앞뒤로 평균내므로 **접근 궤적이 매끄러워져** 초기 정렬이 좋아진 것으로 보인다.
- agg를 켜도 남는 1건은 집은 뒤가 아니라 **집기 자체**에서 실패한 케이스.
