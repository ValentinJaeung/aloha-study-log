| 항목 | 값 |

| 최대 VRAM | **4,840 MiB** (베이스라인 913 MiB 포함 → 학습 순수 사용 ≈ 3.9 GB) |

| 20 epoch 후 val loss | 0.854 (@ epoch 19). 시작 시 67.9 → 학습은 정상 동작 |

### 알게 된 것 3가지

1. **여기서 말하는 "epoch"은 데이터 전체를 한 번 훑는 단위가 아님.**
   `utils.py`의 `EpisodicDataset.__len__`이 에피소드 개수(50)를 반환하고,
   `__getitem__`이 에피소드당 **랜덤 타임스텝 1개만** 뽑음
   → 1 epoch = 45 샘플 ≈ 6 배치. 2000 epoch가 40분이면 끝나는 이유가 이것.
   저자가 "loss가 평평해진 뒤에도 더 학습하면 성공률이 계속 오른다"고 한 것도
   같은 맥락으로 보임 → **성공률이 낮으면 epoch를 늘리는 게 비용 부담이 거의 없음**
   (5000 epoch ≈ 100분).
2. **체크포인트는 100 epoch마다 저장** (`imitate_episodes.py:380`, `if epoch % 100 == 0`).
   개당 336 MB × 21개 + `policy_best` / `policy_last` ≈ **약 7 GB**.
3. **ResNet18 pretrained 가중치(44.7 MB)를 최초 1회 다운로드**함
   (`~/.cache/torch/hub/checkpoints/`). 이제 캐시되어 본 학습에선 이 단계 없음.

## 결과 / 관찰

### 1. WSL viewer 오류 — `OpenGL.error.Error: Attempt to retrieve context when no valid context`

WSLg는 `WAYLAND_DISPLAY`를 설정해둔다. PyOpenGL이 이 변수를 보고 백엔드를 **EGL**로 추측하는데
(`OpenGL/platform/__init__.py:36`), 정작 GLFW는 **X11/GLX** 컨텍스트를 만든다.
서로 어긋나서 `eglGetCurrentContext()`가 `None`을 반환 → 위 오류.

`~/.bashrc`에 3줄 추가로 해결:

```bash
export MUJOCO_GL=glfw
export PYOPENGL_PLATFORM=glx
export GALLIUM_DRIVER=d3d12
```

### 2. 렌더링이 CPU로 돌고 있었음 (llvmpipe)

GPU/CUDA는 정상인데(RTX 2080 Ti, `torch.cuda.is_available() = True`) **OpenGL만** 소프트웨어
래스터라이저를 쓰고 있었다. WSLg용 하드웨어 드라이버 `d3d12_dri.so`는 설치되어 있는데 자동 선택이 안 됨.

| 백엔드 | RENDERER | MuJoCo 오프스크린 렌더링 (480x640) |
|--------|----------|------------------------------------|
| 기본 | llvmpipe (LLVM 20.1.2) | 33.3 fps |
| `GALLIUM_DRIVER=d3d12` | D3D12 (NVIDIA GeForce RTX 2080 Ti) | **156.7 fps** |

약 **4.7배** 차이. 데이터 수집/평가 렌더링 시간이 그만큼 줄어든다.
`MESA_LOADER_DRIVER_OVERRIDE=d3d12`는 효과 없고 `GALLIUM_DRIVER=d3d12`만 동작함.

### 3. 자잘한 것들

- `record_sim_episodes.py`의 인자는 `--onscreen`이 아니라 **`--onscreen_render`**
- `visualize_episodes.py --episode_idx`에는 파일명이 아니라 **숫자만** 넣는다 (`episode_{idx}.hdf5`로 조립됨)
- 데이터는 `act/dataset/`이 아니라 `~/aloha_project/aloha_data/sim_transfer_cube_scripted/`에 있음.
  `act/`에서 실행하면 `--dataset_dir ../aloha_data/...`
- 레포에 **mp4를 재생하는 코드는 없다.** `act-plus-plus/replay_episodes.py`는 이름과 달리
  저장된 action을 시뮬에서 다시 실행해 *새* mp4를 만드는 스크립트다.
  → 재생용으로 `act/play_video.py`를 따로 만들어 둠 (`q`로 종료)

## ⭐ 관찰: val loss가 아직 수렴하지 않았다

`train.log`에서 200 epoch 구간별 최소 val loss를 뽑아보면:

| 구간 | 최소 val loss |
|------|--------------|
| 0–199 | 0.19662 |
| 200–399 | 0.10798 |
| 400–599 | 0.12046 |
| 600–799 | 0.10186 |
| 800–999 | 0.08426 |
| 1000–1199 | 0.06958 |
| 1200–1399 | 0.06262 |
| 1400–1599 | 0.06335 |
| 1600–1799 | 0.04663 |
| **1800–1999** | **0.04584** |

- best epoch가 **1995** — 거의 마지막. 끝까지 계속 내려가는 중이었다.
- 직전 500구간 대비 마지막 500구간이 0.06262 → 0.04584 (**약 27% 개선**)
- 즉 **2000 epoch는 부족했을 가능성이 크다.** 평가 성공률이 기대치(≈90%)에 못 미치면
  하이퍼파라미터를 건드리기 전에 **`--num_epochs`를 5000으로 늘리는 걸 먼저** 시도할 것.
  1 epoch = 45 샘플뿐이라 5000 epoch도 약 96분이면 끝난다 (1부의 "알게 된 것" 1번 참고).
- 저자 튜닝 문서의 "loss가 평평해진 뒤에도 더 학습하면 성공률이 계속 오른다"와도 방향이 맞는다.

추출에 쓴 스크립트:

```bash
cd ~/aloha_project/ckpt
python3 -c "
import re
ep=None; rows=[]
for line in open('train.log', errors='ignore'):
    m=re.match(r'^Epoch (\d+)', line)
    if m: ep=int(m.group(1)); continue
    m=re.match(r'^Val loss:\s+([\d.]+)', line)
    if m and ep is not None: rows.append((ep, float(m.group(1))))
for s in range(0, 2000, 200):
    seg=[v for e,v in rows if s<=e<s+200]
    print(f'{s:5d}-{s+199:<6d} {min(seg):.5f}')
print('best:', min(rows, key=lambda r: r[1]))
"
```
